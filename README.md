# R Analyzer

An ANTLR-based static analyzer for R code. It parses R source into an AST and walks it with visitors to work out which variables a piece of code reads from the outside (inputs), which ones it hands to later code (outputs), and which packages, parameters and configuration variables it depends on.

It was built for [NaaVRE](https://github.com/QCDIS/NaaVRE) (Notebook-as-a-Virtual-Research-Environment), which turns individual Jupyter notebook cells into Docker containers that can be wired together into cloud workflows. A container can only act as a step in such a workflow if its inputs and outputs are known, so that detection has to happen automatically. NaaVRE already did this for Python; this project does it for R.

Written as part of my MSc Software Engineering thesis at the University of Amsterdam (Multiscale Networked Systems group, 2024).

## What it detects

For a given notebook cell, in the context of the whole notebook:

| Category | Meaning |
| --- | --- |
| Inputs | Used in the cell, defined somewhere else |
| Outputs | Defined in the cell, used in a later cell |
| Parameters | Variables prefixed with `param_`, supplied at workflow runtime |
| Configurations | Variables prefixed with `conf_`, global to the workflow |
| Imports | Packages pulled in via `library()` or `require()`, plus dependencies found by `renv` |
| Types | `int`, `float`, `str` or `list`, where they can be determined statically |

### Example

```r
# Cell 1
x <- "foo"
y <- round(1.11, 1)

# Cell 2
print(x)
print(y)
```

Analyzing cell 1 gives:

```
inputs:  {}
outputs: {x: str, y: None}
params:  {}
conf:    {}
imports: {}
```

`x` is typed statically because it is assigned a literal. `y` is not, because its value comes from a function call. Inside NaaVRE the remaining `None` types are filled in by a separate Type Detector, which runs `typeof()` against the live IRKernel after executing the cell and maps `integer`/`double`/`character`/`list` onto NaaVRE's four types. That component lives in the NaaVRE front-end, not in this repository.

## How it works

1. **Lexing and parsing.** The parser is generated by ANTLR 4 from `R.g4` and `RFilter.g4`, taken from the [antlr/grammars-v4](https://github.com/antlr/grammars-v4) repository and modified (see below). `RFilter` runs first and strips the newlines that R treats as whitespace rather than as end-of-statement.
2. **Visitors.** Each production rule in the grammar is labelled, so the generated visitor exposes one method per construct (`visitAssign`, `visitCall`, `visitFor`, `visitExtract`, and so on). The analysis is a set of passes over the tree, one per feature: names, defined variables, undefined variables, imports, configurations, parameters.
3. **Inference.** Inputs are the undefined variables of a cell minus the imports, parameters and configurations. Outputs are variables defined in the cell that are still undefined in another cell. Scope is tracked along the way, so function-local variables, embedded function arguments and loop iterators do not leak into the results.

Visitors are used rather than listeners because they let you decide whether to descend into a node's children and let you return a value from a visit, which matters for things like resolving the type of an arithmetic expression.

## Grammar changes

The upstream R grammar needed a few adjustments to handle real research code:

- Newlines are also stripped before an `else`, so a comment between `if` and `else` no longer breaks parsing.
- `.` is accepted as an expression, for `bquote(a == .(a))`.
- The native pipe `|>` (R 4.1.0) was added to the `USER_OP` rule, alongside magrittr's `%>%`.
- All `expr` production rules are labelled so ANTLR generates a separate visitor method for each.

## Requirements

- [ANTLR 4](https://www.antlr.org/download.html) (developed against 4.13.1)
- Python 3 with `antlr4-python3-runtime`, for the Python target
- A JDK, for the Java target
- R, if you want dependency detection through `renv`

## Build and run

### Python

```bash
antlr4 -Dlanguage=Python3 R.g4 RFilter.g4 -visitor
python3 parseR.py test.r
```

> **After every regeneration**, edit the generated `RFilter.py` and replace
>
> ```python
> (0 if localctx._NL is None else localctx._NL.channel) = Token.HIDDEN_CHANNEL
> ```
>
> with
>
> ```python
> localctx._NL.channel = Token.HIDDEN_CHANNEL
> ```
>
> `RFilter.g4` contains embedded Java that does not translate cleanly to the Python target. See [antlr4#2193](https://github.com/antlr/antlr4/issues/2193).

### Java

```bash
antlr4 R.g4 RFilter.g4 -visitor
javac *.java
java TestR test.r
```

The Python target was chosen so the analyzer could sit inside NaaVRE's Python back-end. That choice is expensive: on the same set of 24 R scripts the Java parser ran roughly 35 times faster.

## Results

Evaluated against two R notebooks used in production on NaaVRE, both annotated by hand with the expected inputs, outputs and parameters per cell.

| Notebook | True positives | False positives | False negatives | Precision | Recall | F1 |
| --- | --- | --- | --- | --- | --- | --- |
| [vl-phytoplankton](https://github.com/QCDIS/vl-phytoplankton/blob/main/service_260224.ipynb) | 48 | 3 | 0 | 0.94 | 1.00 | 0.97 |
| [VeluweProtoDT](https://github.com/LTER-LIFE/VeluweProtoDT/blob/main/Jupyter/Veluwe-proto-DT-v2-GitHub.ipynb) | 28 | 34 | 0 | 0.45 | 1.00 | 0.62 |

No annotated variable was missed in either notebook. The false positives fall into two groups: variables that were genuinely inputs or outputs but had been left out of the annotation because their type (a DataFrame) is not supported by NaaVRE, and implicitly introduced variables, which account for all 32 extra inputs in the second notebook.

Parsing time grows with the number of AST nodes and is unrelated to tree height. Per cell it stays under three seconds with the Python target; analyzing a cell in the context of a full notebook takes seven to thirteen seconds, since every other cell has to be parsed as well.

## Known limitations

- **Implicitly introduced variables.** `dplyr` and `tidyr` functions such as `select()` take bare column names as arguments. Those names resolve against a data frame at runtime, but statically they look like undefined variables, so they are reported as inputs. Fixing this properly needs a knowledge base of which functions introduce names into the environment.
- **Packages that extend the syntax.** R lets packages define new operators. The grammar covers base R and the common additions, but anything more exotic needs a new parsing rule.
- **Static type inference stops at function calls.** R has no equivalent of Python's `typeshed`, and package documentation describes return values in prose rather than in a machine-readable form. Two alternatives were tried and rejected: parsing `.Rd` documentation, and asking an LLM for return types (which confidently returned element types instead of `list` for functions like `seq()` and `str_count()`).
- **Only four types.** `int`, `float`, `str` and `list`, matching what NaaVRE supports. Data frames, matrices and vectors are not distinguished.
